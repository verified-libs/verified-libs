Compare embedded ring buffers by what matters to you

Pick a board, filter on hard requirements, and set weights for the speeds you care about. There is no ranking of ours: without weights the table is alphabetical, and any ranking is the result of your weights, which are stored in the address so the view can be linked. Correctness is not a weight: in every order the table is in three groups, first the configurations with 0 errors in the ISR stress test, then those not tested, then those with errors, whatever their speed. The variants meant for a single context (no interrupt on the other side) are hidden until you clear that box. All numbers and how they were measured: Results and Method.

Producers, consumers and cores

With "any" or SPSC, every speed in the table is for one producer and one consumer. Choosing MPSC, SPMC or MPMC keeps the libraries that document such a mode and whose mode is in our stress test with two interrupts; the line under the library's name says how the library provides it. The speeds and the score are then those of that mode, from a separate benchmark run of the same kind (same scenarios, compiler and flags), and the fastest value in the score is the fastest among these libraries. The calls are timed one at a time, so the numbers are the cost of the mode's protection without contention, not throughput under contention. Zero-copy calls are not timed in these modes, and a mode that does not exist on a board's core (a class that needs compare-and-swap, on Cortex-M0+) shows no numbers there. The ISR stress columns are the SPSC test in every view. "One core" hides nothing: every library here is used on one core. "Two cores" keeps the configurations whose documentation covers two cores running at the same time; with MPSC, SPMC or MPMC it asks the same of that mode.

Rust libraries

The Rust libraries are compiled with rustc (same optimisation level, the core's soft-float target) into a static library that is linked into the same C firmware. The benchmark and the stress tests call them through the same function pointers and time them with the same code as the C and C++ libraries, with the C library's memcpy for both. Their speeds come from a separate firmware of the same benchmark, because the one with all C and C++ libraries fills the SAM D20's RAM. GenMC checks C and C++ only, so the GenMC column is empty for them.

The one-core contract column

GenMC judges C11 and C++ atomics between free-running threads, so it cannot judge the many libraries that rely on one core instead (volatile indices, compiler barriers, interrupt masking). The contract check executes that contract: the library is compiled for the lab host, main's call runs one instruction at a time, and the interrupt's call is made at every instruction (and at every pair of instructions), from every start position and fill level of an eight-slot buffer, with interrupt masking honoured. A configuration passes if every result is one that the calls give one after the other. It is the same for every board; it does not check what a compiler for the target makes of the code (the ISR stress test and its interrupt sweep do that on the boards) or two cores. With a producer/consumer mode chosen above, the column shows that mode's check where one was run, "–" where none was. The negative control and four deliberately broken ring buffers must fail in every run, and do.

The speed benchmark: one image per configuration

Every configuration is measured in a firmware image of its own, linked at a fixed address next to a fixed part that holds the timing code and is the same bytes in every image of a board. So the speed of one library does not depend on which other libraries were built with it, and adding or updating a library changes no other library's image or number. On a core with a cache, an image holding one library is the best case: in an application other code competes for the cache. This is version 2 of the benchmark. In version 1 all libraries were linked into one firmware; its numbers were shown here until this series replaced them, are no longer added to, and its records stay in the repository as an archived series (records/README.md).

What a call costs

A library whose code the compiler can see where it is used (a header-only library, a template, a static inline function) is inlined into the caller and pays no call. A library that is compiled on its own is called. So that every such library pays the same for it, its code lies at least 6144 bytes from the code that calls it, about what a library is away from its caller in a firmware of some size; the adapter between the timing code and the library lies next to the timing code. We measured both: with the library right behind its caller and at this distance. For a single byte the distance costs nothing on the NUCLEO-G0B1RE and the NUCLEO-G474RE, between -2 and +6 cycles on the nRF5340 DK and the SAM D20, less than a cycle on the Pico 2 with its cache on, and on the NUCLEO-H723ZG 3 to 15 cycles (median 6) with the cache on (report). The numbers of a configuration that is inlined whole contain no call at all: ETL's three queues, heapless spsc::Queue and mpmc::Queue, DNedic lockfree mpmc::Queue, Mbed CE CircularBuffer, polycratia spscring, rt-spsc and Zephyr ring_buf. Of other configurations a part is inlined: the single-byte push and pop of every pxq ⚠ configuration contain no call, its block operations do. Whether your firmware gets the same depends on how you build the library.

The small numbers under a speed: placement

The same machine code can take a different number of cycles depending on where it lies in memory (alignment of loops and branch targets to the flash accelerator's or the cache's lines, and to the core's fetch). To show how much, each configuration is built eight times, with its image moved by 0, 4, 8 ... 28 bytes, and every image is run in two passes. The table shows the value at 0 and, under it, the lowest and highest mean of all sixteen runs when they differ at the precision shown. Two configurations whose ranges overlap are not measurably different on that board: a difference smaller than the range comes from the placement, and another firmware would place the code differently. A range is a lower bound: another build can land outside it. The score uses the value at 0.

Code and RAM

"Code / RAM" is what the configuration adds to a firmware on the chosen board, in bytes: flash (code, constants and initial values) and RAM (static data). It is measured by linking the benchmark firmware with that configuration alone and with no library, and taking the difference; the linker drops what is not used. The numbers are for our use of the library: the calls the benchmark makes (one-byte, block and, where the library has them, zero-copy calls), our adapter around them (a few small functions), a buffer of 127 or 128 bytes, and whatever the library pulls in (division or atomic helpers, a critical-section implementation, for the FreeRTOS stream buffer our minimal stand-in for the kernel). The C library's memcpy, memmove and memset are in every firmware and not counted. The compiler and flags are those of the speeds, except that the 32-byte alignment the benchmark gives its timed functions is off, so no padding is counted. A library whose API is used more widely, or with another element type or size, will differ. For the Rust libraries the number includes what their checks pull into a C firmware: bbqueue and embassy-sync Pipe bring Rust's panic and formatting code (several kilobytes), which a firmware written in Rust has already. "+ heap" marks a configuration that allocates its buffer at start-up; that memory is not in its RAM number. Sorting by this column sorts by code size.

How the score is computed

For each speed with a weight above 0, a configuration gets the fastest value on the chosen board divided by its own value: 1 for the fastest, 0.5 for one that needs twice the cycles, and 0 if it has no such API. The score is the weighted mean of these, times 100. Speeds are mean cycles per call with the code in flash and the cache or flash accelerator on; "64-byte block" is cycles per byte (mean of write and read); "zero-copy" is the cycles of the library's own calls around a 64-byte transfer (mean of write and read). Lower cycles are better; a higher score is better. The score says nothing about correctness, code size, RAM use, API or license: use the filters and the other columns for those.

⚠ marks the project owner's own library. It is tested with the same suite as every other library and more (every documented mode and topology), and like every result its numbers can be repeated outside the project (Reproduce). A row with no stress result was not in the campaign shown, which is not the same as 0 errors. The stress counts are from the newest night campaign on each board, added together with the nights before it as long as the test did not change in between (the same stress firmware, libraries and compiler flag rotation); the campaigns used are named under the table.
