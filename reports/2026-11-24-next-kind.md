Common to every kind, and a decision before any of them goes to the
boards: the export check holds all of `firmware/` as the test sources of
the ring-buffer records, so the first file of a second kind there stops
the export of all 265 version 2 records (step 1, tested). The check has
to learn test sources per kind, or the second kind lives elsewhere. This
is a change of method for the export and the owner's to decide. Kind C
pays it as well, because it adds configurations to the ring-buffer
benchmark.

Further kinds named only, not surveyed: fixed-point and small math
routines (the owner's own math_bits ⚠ would be among them, so the kind
would need the conflict-of-interest rules from the start); event flags
and software timers of RTOSes (small, interrupt-driven); serialisation
(nanopb and others; correctness by fuzzing).

## Recommendation: A, fixed-block pools used from interrupts

**Why A.**

- It is the next hard case after ring buffers for the same readers: in drivers
  and network stacks the buffer an interrupt fills is often a pool block
  (lwIP's `memp` is one). It is interrupt-driven, and its lock-free
  implementations (CMSIS-RTX on Armv7-M and Armv8-M, heapless) raise the
  question the project exists to answer: does the code hold under every
  preemption on the real core?
- What makes the project different carries over: the ISR stress test,
  the interrupt sweep, the two-interrupt test and the contract check on
  the host model all apply with a new judge, and the benchmark of version
  2 applies as it is.
- It adds a number no page has: the longest time a pool keeps
  interrupts off per call, which a real-time reader needs and cannot read
  from the documentation.
- The candidates are the pools most firmware actually runs (Zephyr,
  CMSIS-RTX, ThreadX, RT-Thread, NuttX, uC/OS-III, lwIP), each with a
  clear documented promise about interrupts to check.
- A first series costs a moderate number of flash writes (~20–30).

**What speaks against it.**

- Most candidates live inside an RTOS. Each needs stubs to run without
  its kernel, as the FreeRTOS stream buffer did; that is per-library
  work, and a reviewer may ask whether the stubbed pool is the one users
  run.
- A pool is simple code. The test is worth most for the lock-free
  implementations and for the interrupt-off time; for a pool that turns
  interrupts off around four lines, a pass is expected.
- The host model of LDREX/STREX is new work in `verify/contract`, the
  part of the project's tools that reviewers read most closely.

## Runner-up: D, CRC in software

D is the safest second kind: no concurrency, so no new judge, a
correctness proof that is complete, a measurement whose value lies in the
hardware (what a table in flash costs with wait states, an accelerator, a
data cache or external QSPI flash), and many candidates with tables of
several sizes. It would also be the cheapest way to make the machinery
hold two kinds (the export per kind, a second page, the MCP server's
tools), because the test itself is simple. Against it: it uses little of
what makes the project different, its first series is the largest in
flash writes, and a reader may find a CRC too easy to need a registry.

A possible order, if the owner wants both: D first as the kind that
generalises the machinery with the least risk in the test itself, then A
on the generalised machinery. The night's pilot (step 4) is made for A,
the recommendation; a pilot for D would be smaller.

## Unknowns

- How many RTOS pools can be run without their kernel with honest stubs
  (FreeRTOS's stream buffer could; the others were not tried).
- Whether LDREX/STREX can be modelled on the host model faithfully
  enough for the lock-free pools (Cortex-M clears the exclusive monitor
  on exception entry and return; the model would do the same).
- The flash-write guesses: none was counted from a slot table.
- Whether the export check's change (test sources per kind) is
  acceptable to the owner, and its cost.
- Licences were taken from licence files, not from GitHub's licence
  field, this night (the API was not used); each must be checked again
  before a library is fetched for the lab.

## Review and decision (2026-11-24)

The report was reviewed in the daytime. Checked again: the export finding
of step 1 (a new file under `firmware/` stops all 265 records, the same
file outside it stops none), the pilot's host test (the same output), and
five of the surveys' source claims in the clones (CMSIS-RTX, RT-Thread,
heapless, lwIP, ThreadX), which held.

The review adds to "What speaks against it" for A:

- Twelve of the seventeen pools live inside an RTOS or a network stack.
  A reader does not choose an RTOS for its pool, so a comparison page
  has few real choices to offer; the libraries a bare-metal project can
  pick by themselves are few, and most of those have no lock of their
  own.
- The hard cases are CMSIS-RTX's lock-free path, heapless and perhaps
  atomic-pool. None of them was tried in the pilot, which took the three
  pools that were easiest to build.
- The new number, the longest time with interrupts off, would be
  measured on a pool without its kernel and on the path where no thread
  waits. In a running RTOS the longest time is on the other path. The
  measurement is also not designed yet.
- A first means a new judge, a new verdict, a model of LDREX/STREX,
  kernel stubs and new firmware at the same time as the machinery learns
  to hold two kinds.

And one for D that the report does not name: libraries with the same
algorithm may compile to the same loop, so that the result is one per
algorithm and board, not one per library. This is not measured; the
plan for D asks the host work to answer it first.

**Decision of the owner: D first, then A in a narrower form.** D makes
the machinery hold two kinds with the simplest test, and its result
(what a table in flash costs on six different flash designs) is one only
a lab with the boards can give. The plan for D is
[lab/plans/2026-11-24-crc-kind.md](../lab/plans/2026-11-24-crc-kind.md);
its first series is to start with at most 20 configurations, not 40.

Before A is started, two checks on the host, without a board: can
CMSIS-RTX's pool be built alone, and can LDREX/STREX be modelled on the
host model. If they fail, A loses its hard cases, and kind C is looked
at again.
