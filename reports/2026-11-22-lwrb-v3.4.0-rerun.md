# Re-run with lwrb v3.4.0: every test at one commit, all six boards (2026-11-21/22)

lwrb released v3.4.0 (`b8534fd15925`), which adds functions for one byte,
`lwrb_write_byte` and `lwrb_read_byte`. The pin moved from v3.3.0
(`413b7093dcad`), and lwrb's single bytes are now measured through the new
functions (DECISIONS 2026-11-22). The pin and the adapter are test
sources, and a record must name sources the reader has, so everything the
site shows was measured again at one commit, `a7a206190337`, the same way
as in the [publication re-run](2026-11-20-publication-rerun.md):
`lab/tools/publication-rerun.sh 5 5` on each board (code size, the three
benchmark sets at eight code placements, five hours of the ISR stress
test, five hours of the two-interrupt test). Start 2026-11-21 23:42 UTC;
the last board finished 2026-11-22 12:52 UTC. The method is the frozen
one (tag `v1-method-freeze-2`); no test and no campaign script changed.

## Result

- **lwrb v3.4.0: no errors** in its 108 runs of the ISR stress test (13
  of them with the two sides on the Pico 2's two cores), and the model
  check passes for the byte functions and for the block calls.
- **lwrb's single bytes are 3 to 4 times faster** through the new
  functions (table below). Its blocks and its zero-copy calls cost what
  they did, within 4 %. Its code grew by 108 to 132 bytes.
- **ISR stress test: no errors in any real library in any run** (108 runs
  on six boards, all valid).
- **Two-interrupt test: no errors in any library in its documented mode in
  any valid run** (324 runs on six boards, 322 valid). lwrb is a
  single-producer, single-consumer library and is not in this test.
- No step failed: no benchmark image needed a second try, no stress run
  was repeated, no board was power-cycled.
- **The other libraries' speed numbers moved too**, although their code
  did not change, because all the C and C++ libraries share one benchmark
  image and its layout changed. Most moves are small; 29 of 666 means left
  the placement range shown before, and one number moved by 57 % (see
  "What moved in the other libraries").
- The two invalid runs of the two-interrupt test are the same two entries
  of the rotation as on 2026-11-19/20.

## Benchmarks

24 images per board (three sets at placement shifts 0, 4, ..., 28), 25 on
the nRF5340 (Nordic's nrf_ringbuf, one placement). All 145 ran at the
first try. The records are in `records/bench/` (151 with the six code-size
records).

Only one of the benchmark images changed with the pin: the one with the C
and C++ single-producer libraries, which holds lwrb. The Rust image, the
multi-producer image and Nordic's were byte for byte those of the
publication re-run (built at both commits and compared before the run).
They were written and measured again all the same, and gave the same
numbers: all 66 means of the Rust libraries and the 5 of Nordic's
nrf_ringbuf are identical to the last digit recorded, and so are 716 of
the 720 numbers of the multi-producer set (means and range ends); the
other four differ by at most 0.03 %. An image that is the same gives the
same cycle counts on these boards.

### What moved in the other libraries

The C and C++ single-producer libraries are linked into one image. lwrb's
code is 108 to 132 bytes larger, so the code after it lies at other
addresses, and the alignment the benchmark gives each timed function does
not remove all of that. Of the 666 means of the configurations other than
lwrb (C and C++, the six boards):

| | Means |
|---|---|
| identical | 396 |
| within 0.5 % | 548 |
| moved by more than 2 % | 43 |
| outside the placement range shown before | 29 |

## ISR stress test

`firmware/nrf5340-rb-stress/overnight.sh`, five hours per board, each
library from its own image after its own reset, gcc -O2, the rotation of
17 entries grouped by code location. A run is valid when the control (a
deliberately broken buffer) was caught in it. The runs per board, mode,
code location and cache setting are those of 2026-11-19/20. So are the
images of every library but lwrb: by the checksums in the records, 39 of
the 40 library images per code location are byte for byte the same, and
the one that differs is lwrb's.

Summed over the library rows of the six campaign reports: 11.6 × 10⁹ bytes
through the buffers under 6.3 × 10⁹ interrupts. The interrupt sweep made
114 to 539 million trials per board, with the interrupt inside the call
in 76 to 82 % of them.

**lwrb v3.4.0** was in every run: 9, 9, 27, 13 and 8 runs on the nRF5340,
the G0B1, the G474, the H723 and the SAM D20, and 42 on the Pico 2 (13 of
them on two cores, which lwrb documents). No errors. The stress test
moves its single bytes through the byte functions too; its zero-copy
calls were stressed on the G474, the H723 and the Pico 2.

**Errors only where they are expected**, as in every campaign before:

- on every board, the three variants their own projects do not call
  interrupt-safe: wizard97 as shipped, Arduino RingBufferN as shipped and
  RT-Thread rt_ringbuffer without a lock;
- on the Pico 2 with the two sides on two cores, the nine single-core
  designs (their interrupt lock does nothing against the other core).

**Mutants** (four buffers with one deliberate defect each): the sweep
caught every mutant in every sweep run in the directions where its defect
can show, on all six boards. With random interrupts the weak spots are
the same as before: "drain re-reads head" was caught in 12 of 27
single-byte runs (11 of 27 on 2026-11-19/20), and "full test misses the
wrap" in the direction main to interrupt in 16 of 20 block runs.

**Starved parts.** The same three entries of the rotation as on
2026-11-19/20, at the fastest interrupt rate on the two Cortex-M0+
boards. A starved part is reported, not counted as a pass and not as an
error:

| Run | Starved |
|---|---|
| SAM D20, single, `samd20-rb-stress-single-20261122T015316Z` | FreeRTOS stream buffer (interrupt to main), embassy-sync Pipe (main to interrupt), NuttX circbuf (both directions) |
| SAM D20, block, `samd20-rb-stress-block-20261122T022250Z` | NuttX circbuf (interrupt to main) |
| G0B1, single, `stm32g0b1-rb-stress-single-20261122T013250Z` | NuttX circbuf (both directions) |

**Not reached**, as on 2026-11-19/20: the rotation's zero-copy entries
come after the flash entries for single bytes and blocks, and five hours

5 on the G474, 3 on the H723 and 8 on the Pico 2. The same three boards
have no run from SRAM.

## What this run says about re-running

Three things were measured here that the project did not know before:

- The same image gives the same numbers (787 of 791 identical, the rest
  within 0.03 %), and the two-interrupt test with the same images gave
  the same run counts, the same valid runs and no errors.
- A change in one library's code moves the numbers of the libraries that
  share its image, on the nRF5340 by more than their placement range.
- Most of what ran had not changed. Of the 24 or 25 benchmark images per
  board, 16 or 17 were the same (the Rust, multi-producer and Nordic
  sets). In the stress tests each library runs from its own image: every
  image of the two-interrupt test, and every image of the ISR test except
  lwrb's, is byte for byte the one of 2026-11-19/20. Running them again
  changed nothing on the page beyond the campaigns' new seeds.

So measuring everything again for one library's new version buys little
for the images that did not change, and it is what the record rule
requires today. A proposal for a rule that keeps the records of
unchanged images is in the plan
([lab/plans/2026-11-22-same-image-rule.md](../lab/plans/2026-11-22-same-image-rule.md)); it is a
proposal, and nothing in the tools has changed.
