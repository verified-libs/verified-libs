Publication re-run: every test at one commit, all six boards (night 2026-11-19/20)

Everything version 1 shows is measured again here, at one commit: 8d8880f4bf78 (tag v1-method-freeze-2). The public repository has no history, so a record must name sources the reader has (DECISIONS 2026-11-16). lab/tools/publication-rerun.sh 5 5 ran on each board, one step after the other: code size, the three benchmark sets (SPSC, multi-producer, Rust) at eight code placements, five hours of the ISR stress test and five hours of the two-interrupt stress test (MPSC/SPMC). Start 2026-11-19 17:33 UTC; the last board finished 2026-11-20 06:44 UTC.

Result

  • ISR stress test: no errors in any real library in any run (108 runs on six boards, all valid).
  • Two-interrupt test: no errors in any library in its documented mode in any valid run (324 runs on six boards, 322 valid).
  • The control was caught in every run of the ISR test and in 322 of the 324 runs of the two-interrupt test. The two where it was not caught are left out: both on the nRF5340, MPSC mode, random interrupts at prescaler 2.
  • No step failed: no benchmark image needed a second try, no stress run was repeated, no board was power-cycled.
  • The speed numbers are the earlier ones within their placement ranges.
  • Not reached in the five hours: the zero-copy (DMA API) entries of the ISR rotation on the nRF5340, the G0B1 and the SAM D20 (see below).

Benchmarks

24 images per board (three sets at placement shifts 0, 4, ..., 28), 25 on the nRF5340 (Nordic's nrf_ringbuf, one placement). All 145 ran at the first try. The records are in records/bench/ (151 with the six code-size records).

Against the numbers shown before (records of 2026-11-13 to 2026-11-16, made at other commits), seven rows of the speed table changed. Five moved by one cycle per call or by at most 0.5 cycles per byte. The other two:

  • embassy-sync Pipe on the G474: 229 / 217 cycles for push / pop, before 190 / 174. Both pairs lie in its placement range (190-235 / 174-217).
  • bbqueue on the H723: push 150 cycles, before 144. Its range was 144-150 before; in this build it is 150 at all eight placements.

In both cases the code landed at other addresses in this build, and the speed of that library on that board depends on them. This is what the placement ranges on the comparison page are for. The bbqueue case also shows their limit: eight placements of one build need not show the whole range, so a range is a lower bound on how much a number can move.

Placement, over the 1,002 numbers that have a range: 703 do not move at all over the eight placements and 826 move by 1 % or less. The largest ranges:

The cause has not been looked into; the Pico 2 fetches its code through the XIP cache from QSPI flash. Version 1 shows the number with its range.

Summed over the library rows of the six campaign reports: 11.6 × 10⁹ bytes through the buffers under 6.4 × 10⁹ interrupts.

Errors only where they are expected, as in every campaign before:

  • on every board, the three variants their own projects do not call interrupt-safe: wizard97 as shipped, Arduino RingBufferN as shipped and RT-Thread rt_ringbuffer without a lock;
  • on the Pico 2 with the two sides on two cores, the nine single-core designs (their interrupt lock does nothing against the other core).

Mutants (four buffers with one deliberate defect each): the sweep caught every mutant in every sweep run in the directions where its defect can show, on all six boards. With random interrupts the weak spots of the earlier campaigns are the same: "drain re-reads head" was caught in 11 of 27 single-byte runs, and "full test misses the wrap" in the direction main to interrupt in 16 of 20 block runs.

Starved parts. At the fastest interrupt rate (prescaler 0) the main loop of a slow library on a slow core can get too little time to finish next to the interrupt load. The test reports that as starved, not as an error and not as a pass. It happened in three runs:

Run Starved
SAM D20, single, samd20-rb-stress-single-20261119T194650Z FreeRTOS stream buffer (interrupt to main), embassy-sync Pipe (main to interrupt), NuttX circbuf (both directions)
SAM D20, block, samd20-rb-stress-block-20261119T201617Z NuttX circbuf (interrupt to main)
G0B1, single, stm32g0b1-rb-stress-single-20261119T192422Z NuttX circbuf (both directions)

The site data now leaves such a run out of that library's run count and says so next to the number (site/gen_libdata.py, "not_counted"; on the comparison page "1 run not counted: starved by the interrupt load"). Before this night's evaluation it was counted with the passes, which is not what the method page says. The per-mode summary in records/campaign/ (what repeat.sh compares a repetition with) is made by the frozen summarizer and still counts the run for the library; it has no errors either way.

Not reached. The rotation's zero-copy entries (dma, sweep-dma) come after the flash entries for single bytes and blocks. On the three slowest boards a run of all libraries takes about 40 minutes, so five hours ended before them: the re-run has no ISR stress run of the zero-copy API on the nRF5340, the G0B1 and the SAM D20. It has them on the G474 (5), the H723 (3) and the Pico 2 (8). The same three boards have no run from SRAM (the SAM D20 has no such image at all). The comparison page shows what was run; nothing from earlier commits is mixed in.

Two-interrupt test (MPSC / SPMC)

firmware/rb-mp-stress/campaign.sh, five hours per board, each library from its own image, 1,000,000 values per library and run at prescaler 1 and 2, fewer at 3 and 4. New in this campaign (DECISIONS 2026-11-19): every run at prescaler 3 and 4 uses aimed interrupts, and random interrupts are used at prescaler 1 and 2 only. In the campaign of 2026-11-17/18 half the slow-rate runs were random, and 100 of 850 runs were invalid because the control was not caught in them (report). This time two of 324 are: runs 2 and 10 on the nRF5340, both MPSC with random interrupts at prescaler 2 and the code in flash. With aimed interrupts the control was caught in every run on every board. So random interrupts can miss the control at prescaler 2 as well: on the nRF5340 in 2 of its 13 random runs (2 of the 3 at that rate in MPSC mode, the two with the code in flash). What the evaluation changed in the tools

No firmware and no campaign script changed (frozen until the export). Changed on the host side only:

  • site/collect_records.py takes, from a campaign directory, the first run that passed of each mode (for the two-interrupt test: of each mode with random and with aimed interrupts), not every record. records/stress/ then holds 58 records (11 MB; the sweep records carry every sweep position); the campaign reports here and records/campaign/ cover all runs.
  • site/gen_libdata.py and the comparison page: starved runs, as above.
  • lab/tools/public-export.py, verify-build.sh and repeat.sh: a record names the commit it was made at, and the records can only be committed after it. The export now lists the commits whose test sources (firmware, board table, the two scripts the tests call) are byte for byte those of the exported tree (SAME_SOURCES), the two tools accept a record from any of them, and the export refuses a tree with a record from any other commit.
