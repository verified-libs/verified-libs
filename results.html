Results: embedded ring buffers (all in one place)

Status: harness development, not published results. Numbers are facts about the pinned versions, configuration and board below, not general rankings. ⚠ marks the project owner's own library; under principle 6 it is tested with the same suite as every other library and more (every documented mode and topology), and like every result its numbers can be repeated outside the project. Defects are reported to maintainers first (principle 5) and stay unpublished for 90 days from sending.

Updated 2026-11-20. Six boards: nRF5340 DK (application core), Raspberry Pi Pico 2 (RP2350), NUCLEO-G474RE, NUCLEO-H723ZG, NUCLEO-G0B1RE and SAM D20 Xplained Pro (method). One-core contract check

2026-11-16 (commit 7ed89e4): each library's own code, compiled for the host, with the interrupt's call made at every instruction of the main loop's call from every start state of a small buffer, and at every pair of instructions (two interrupts in one call) from the start states at the wrap; interrupt masking is modelled. The result of each trial is compared with an ideal FIFO. Method: contract check.

38 configurations, 7,039,483 trials: 35 pass, 3 fail. The three that fail are the variants their own projects do not call interrupt-safe (wizard97 as shipped, Arduino RingBufferN as shipped, RT-Thread rt_ringbuffer without a lock). The 35 include pxq ⚠ in all four topologies and with reserve/commit, and the Rust libraries. Per configuration: the contract-check column of the comparison.

Notes per library

  • [N1] pxq uses volatile for its documented contract (ISR ↔ main loop on one core). Under the C11 model that is a data race by definition, so it is checked against its contract (the one-core contract check), not with the plain C11 check.
  • [N2] AndersKaloer uses plain variables; this build happens to keep a safe store order, which the language does not guarantee. Its queue function overwrites when full; the adapter checks for space first.
  • [N3] diffstorm up to 547d0812 had two defects, found by GenMC and a host reproducer: the 1-byte overwrite flag was accessed with 32-bit loads/stores, so uninitialised padding could turn overwrite mode on (silent data loss), and the consumer lacked acquire ordering (matters across cores). The stress test passed only because the test object is in zeroed memory. Reported on 2026-11-08; the maintainer fixed both the same day (91ae20b). The row is 11e05d60: GenMC passes, the reproducer gives the correct result, and the board stress (single, block, flash and SRAM, 2026-11-09) has 0 errors. The maintainer agreed on 2026-11-09 to publication before the 90 days are over; when the project goes public is the owner's decision. See the finding.
  • [N4] Without user-supplied RB_ATOMIC_START/END macros wizard97 is not ISR-safe, as its own header warns. With them: 0 errors (wizard97 + PRIMASK macros).
  • [N5] pxq 1.4.0 copies blocks with an element loop instead of memcpy. That makes the single-byte pop faster (31 → 20 cycles) but 64-byte blocks about 2.2× slower (3.1 → 6.8 cycles/byte with code in flash, about 3× slower from SRAM). The unreleased 1.4.1 (fix/word-copy, 01f54417) uses the loop up to 8 bytes and memcpy above. It measured 17 / 20 for one byte and 3.0 cycles/byte at 64 bytes. Which version is faster depends on the C library's memcpy: with ST's toolchain it is a byte loop. Linked against newlib's byte-loop memcpy stub (as ST ships it), 1.4.0 is the fastest of the three from 16 bytes up (64 bytes, flash -O2: 1.3.2 575 / 575, 1.4.0 465 / 402, 1.4.1 566 / 564 cycles). See the 2026-11-08 report.
  • [N6] TinyUSB: 55 valid overnight runs (2026-11-08/09), 25.6 million bytes under 114 million interrupts; not in the first two campaigns.
  • [N7] pxq ⚠: its MPSC, SPMC and MPMC modes mask interrupts, so they are for one core; with the producers or consumers on the Pico 2's two cores they give errors, and reserve/commit starves (not counted: not a documented use; see the validation report). On the NUCLEO-H723ZG its indices share a cache line with its data; a DMA can only use it in non-cacheable memory (DMA report).

ISR stress campaigns

Every campaign so far: no errors in any real library in any valid run. The errors are where they are expected: the variants their own projects do not call interrupt-safe, and on the Pico 2 in two-core mode the single-core designs whose interrupt lock does nothing against the other core.

Since 2026-11-15 the test runs each library from its own image after its own reset, with the run's parameters set at run time. The comparison page and the records show the publication re-run, the first campaign below; the campaigns after it used the method before that, at earlier commits.

Publication re-run (night 2026-11-19/20)

Every test again at one commit (8d8880f4bf78), five hours of the ISR stress test per board, gcc -O2: 108 runs on the six boards, all valid, no errors in any real library. 9 runs on the nRF5340 and the G0B1, 27 on the G474, 13 on the H723, 8 on the SAM D20 and 42 on the Pico 2 (15 of them with the two sides on its two cores). The sweep caught every mutant in every sweep run. Three runs at the fastest interrupt rate starved a slow library on the SAM D20 or the G0B1 (FreeRTOS stream buffer, embassy-sync Pipe, NuttX circbuf); such a run is reported and not counted for that library. The five hours did not reach the zero-copy entries of the rotation on the nRF5340, the G0B1 and the SAM D20, so the zero-copy API has stress runs at this commit on the G474, the H723 and the Pico 2 only. Details, the speed numbers against the earlier ones and the flash writes: reports/2026-11-20-publication-rerun.md.

Five flag sets, Rust libraries, new layout (night 2026-11-13/14)

209 valid runs of 211 on the six boards: no errors in any real library, with five compiler flag sets (-Os, -O3, -O2 + LTO, -O2 + clang and, new, -Os + LTO) and the three Rust libraries (heapless spsc::Queue, bbqueue, embassy-sync Pipe; 165 to 209 valid runs each, 0 errors). The one run too slow for the time limit and the one probe failure (retried, passed) are explained in reports/2026-11-14-night-flags-placement.md, with the placement experiment for the Rust and multi-producer sets.

Interrupt sweep, mutants and wave 4 (night 2026-11-12/13)

The second night on all six boards added three things to the stress test.

  • Interrupt sweep (modes sweep, sweep-block, sweep-dma): instead of interrupts at random times, one interrupt per call at every delay from the start of the call, from five fill levels and 256 start positions, so every instruction boundary of a call is hit on purpose. After each sweep the buffer is drained and the byte count checked (bytes lost, bytes too many).
  • Mutants: four ring buffers with one deliberate defect each, next to the negative control, to show which mode can find which kind of defect. The sweep caught every mutant in every run in the directions where its defect can show (55 of 55 and 70 of 70 runs). The random modes sometimes miss: one mutant was caught in 39 of 89 random single-byte runs, another in 67 of 84 random block runs in one direction. Two mutants cannot fail in the main→interrupt direction on one core; on the Pico 2's two cores they are caught in both.
  • Wave 4: NuttX circbuf, Arduino RingBufferN as shipped (its maintainers call it not interrupt-safe; reported, not counted) and Arduino SafeRingBufferN: 28 libraries and variants in all.

422 valid runs of 427: no errors in any real library on any board. The errors are where they are expected: the two variants their own projects call unsafe (wizard97 and Arduino RingBufferN as shipped), in every mode on every board, and on the Pico 2 in two-core mode the single-core designs whose interrupt lock does nothing against the other core. Four runs on the nRF5340 were too slow for the time limit (not hung) and one SAM D20 run was invalid because its control was caught in one direction only. Details, the per-mode tables and the choice of 256 start positions: reports/2026-11-13-night-sweep-mutants-wave4.md.

Stress, first night on all six boards (2026-11-11/12)

502 valid stress runs across the six boards (59 of them SMP on the Pico 2), 4.0 G bytes and 12.6 G interrupts through the 20 pre-wave-3 libraries: no errors in any real library. Only the expected failures showed: wizard97 as shipped (not ISR-safe by its docs) everywhere, and the single-core designs in SMP mode. Earlier campaigns on the nRF5340 alone (2026-11-07 to 09: 101 valid runs, 0 errors in every real library): 2026-11-07, 2026-11-08.

Compilers on the STM32 boards (2026-11-12)

The libraries built with Arm GCC 14.2, clang 21.1, and ST's two compilers from STM32CubeCLT 1.22.0 (local image only, STM32 boards only). ST Arm Clang generates byte-identical code to upstream clang for these libraries; GNU Tools for STM32 14.3 measures the same as Arm GCC in all but two cells. ISR stress with both ST compilers and the Omax preset (27 runs): 0 errors, control caught. gcc and clang are within ±4 % on the M4 and M7; on the M0+ clang is 24 % slower because it turns every atomic load and store on ARMv6-M into a library call. ST's Omax preset gains 2-6 % over clang -O3, still behind gcc -O3: reports/2026-11-12-compilers-stm32.md. On all six boards (2026-11-16, adding Arm Toolchain for Embedded 23.1 and the Zephyr SDK's GCC 14.3): Zephyr's GCC measures like Arm GCC, ATfE like upstream clang, and clang-family code is 2-5 % slower for single bytes on the M33/M4/M7 and 20-24 % slower on both M0+ boards (atomics as library calls on ARMv6-M); 0 errors in every run: reports/2026-11-16-compilers-six-boards.md. Five C libraries' memcpy/memmove/memset/memcmp (2026-11-17): newlib, newlib-nano and Zephyr's picolibc copy equally fast on the M33/M4/M7; on the M0+ Zephyr's picolibc is up to 59 % slower for 64 bytes, LLVM libc slightly faster, and ATfE's size-built picolibc 3-5 times slower; up to 17 library configurations' block numbers move by more than 5 %: reports/2026-11-17-c-libraries.md.

What the numbers say

  • Single bytes: on every board pxq, jnk0le, polycratia and rt-spsc are among the fastest (17–24 cycles on the nRF5340); the general stream APIs (lwrb, FreeRTOS stream buffer, embassy-sync Pipe, bbqueue) are the slowest (about 175–300 there), because one byte goes through several calls and memcpy.
  • Blocks: the libraries that copy with memcpy (NuttX circbuf, Zephyr ring_buf, RT-Thread, DNedic lockfree, ece-mohammad, TinyUSB, lwrb, the FreeRTOS stream buffer, Mbed CE, the Rust stream buffers) need 2.5–6 cycles per byte at 64 bytes on the M4, M7 and M33, about 10–15 on the M0+; the ones that copy element by element 6–130.
  • Zero-copy (DMA): pxq, lwrb, ece-mohammad, TinyUSB, Zephyr ring_buf, NuttX circbuf and bbqueue have such an API. Its cost is fixed per transfer, independent of the number of bytes.
  • Correctness: every library that is interrupt-safe in the configuration its documentation asks for showed 0 errors in the ISR stress test. The ten atomics-based libraries checked with GenMC pass under the C11 memory model (diffstorm after its fix), so they are also correct between two cores within the test's bounds. The diffstorm defects were found by GenMC and a targeted reproducer, not by SPSC stress testing, and reported to the maintainer on 2026-11-08.
