Night campaign with the interrupt sweep, mutants and wave 4 (2026-11-12/13)

Stress campaign on all six boards (lab/tools/night-all.sh, each board with its own copy of the repository at commit 25c64d2), 18:45 to about 07:00 UTC (the nRF5340 until 08:45: it was waiting in a run that was too slow, see below). New since the campaign of 2026-11-11/12:

  • the interrupt sweep (modes sweep, sweep-block, sweep-dma): one interrupt per call, at every delay from the start of the call, from five fill levels and 256 start positions; 6 of the 17 rotation entries;
  • the count check: after every sweep the buffer is drained and the number of bytes compared with what went in and out (bytes lost and bytes too many are reported);
  • four mutants (mutants.c): ring buffers with one deliberate defect each, to show which test modes can find which kind of defect. They do not decide whether a run is valid; the negative control does, as before;
  • wave 4: NuttX circbuf, Arduino RingBufferN as shipped (ArduinoCore-API issue 195 says it is not interrupt-safe; reported, not counted) and Arduino SafeRingBufferN. 28 libraries and variants, plus the control and the mutants.

No errors in any real library in any valid run, on any board: 422 valid runs of 427. The errors are where they are expected: the two variants their own projects call unsafe (wizard97 as shipped, Arduino RingBufferN as shipped), on every board and in every mode, and on the Pico 2 in SMP mode the single-core designs whose interrupt lock does nothing against the other core (ETL queue_spsc_isr and queue_spsc_locked, wizard97 with PRIMASK macros, Arduino SafeRingBufferN).

  • The sweep finds every mutant in every run in the directions where the defect can show (55 of 55 and 70 of 70), where the random modes sometimes miss: "drain re-reads head" is caught in 39 of 89 random single-byte runs, "full test misses the wrap" in 67 of 84 random block runs in the main→interrupt direction.
  • Two mutants cannot fail in the main→interrupt direction on one core (the defective call then runs in the interrupt and is not interrupted itself); on two cores (Pico 2, SMP) they are caught in both directions ("drain re-reads head" in 16 of 19 random single-byte SMP runs one way, in every run otherwise).

Runs that did not count

  • nRF5340 DK, 4 runs: sweep-block with the cache off was too slow, not hung. At 256 start positions it needs about 1.7 hours on this board; run.sh gave up after about 1.5 hours, the campaign power-cycled the board and tried once more, twice (about 6 hours of the night). Checked afterwards: the same build and seeds finish with 16 start positions (0 errors, control caught). run.sh now tells a slow run from a hung one (two reads of the result block; exit 4, no power cycle, no retry). The same configuration took 95 minutes on the G0B1 and 94 on the H723, close to the limit.
  • SAM D20, first campaign of the night stopped by hand: run 0 (single bytes, prescaler 0, 300 000 bytes) passed the same time limit with the larger library list. Restarted at 20:39 UTC with a 2-hour limit; the table shows that campaign. That run took 83 minutes.
  • SAM D20, 1 run invalid (dma, prescaler 0): the negative control was caught in one direction only (9 950 errors interrupt→main, 0 main→interrupt with 298 interrupts in the measured part: the main loop was starved). 0 errors in the real libraries; the run is not counted.

Time per run

sweep-block at 256 start positions is by far the longest entry of the rotation: 10 to 14 minutes on the fast boards, 38 to 88 on the slow ones (cache on, flash; up to 95 with the cache off), against 2 to 18 for a random block run. The slow boards got 23 to 38 runs in the night, the fast ones 62 to 160. Open: fewer start positions for sweep-block, on all boards alike.

After the campaign: board check of the work since 25c64d2

Short runs on all six boards at 76c9581 (20 000 bytes or 16 start positions; records in ~/lab-runs/val-20261113/): the six stress modes, the benchmark, and the multi-producer/multi-consumer stress (MPSC and SPMC), plus the SMP modes on the Pico 2. All 61 runs valid, no errors in real libraries in their documented mode. Records name their source commit.

  • Rest of wave 4 (first board runs): RT-Thread rt_ringbuffer with interrupts off per call, Mbed CE CircularBuffer and moodycamel ReaderWriterQueue: 0 errors on one core on every board. RT-Thread as shipped, without a lock (no claim; reported, not counted): 76 errors. With the other side on core 1, the two interrupt-lock designs fail as expected (RT-Thread with interrupt lock, Mbed CE); moodycamel, which is documented for two threads, has 0 errors.
  • SMP sweep, first board run: it found nothing it should have found. Single-byte sweep-smp reported 0 errors for wizard97 as shipped, Arduino RingBufferN as shipped and three of the four mutants. Cause: core 1 has to notice the start flag first, so its call always came after the first instructions of core 0's call, and it moved in steps of its polling loop. Fixed (a fixed lead on core 0, delay steps of about one cycle on core 1): every mutant, every single-core design and both unsafe variants are now caught in both directions in sweep-smp and sweep-smp-block; the multicore-documented libraries stay at 0 errors. This is what the mutants are for: the run was "valid" by the negative control alone.

How many start positions: 16 to 256 (NUCLEO-G474RE, sweep-block)

Question: the sweep runs with 256 start positions take up to 1.7 h on the slowest board; would fewer do? Measured on one board at 4e8e856: 16, 32, 64, 128 and 256 start positions, three seed pairs each, cache on, code in flash, -O2 (15 runs, all valid, 0 errors in the real libraries; records in ~/lab-runs/reps-20261113/nucleo-g474re).

  • The mutants and the two unsafe variants do not distinguish the settings: their error counts grow linearly with the number of start positions, and the weakest ("full test misses the wrap") still has 85 to 101 errors per direction at 16. "Pop without lock" and "drain re-reads head" are caught isr→main only at every setting, as in the campaign.
  • The rarest real finding does: RT-Thread without a lock, isr→main, is missed in all three runs at 32 and in two of three at 64, and found in every run from 128 up. main→isr was found in all 15 runs (2 to 4 errors at 16, 42 to 82 at 256). From 64 to 128 the isr→main count grows far more than twofold; why has not been examined.
  • The times at 16 and 32 are bounded below by run.sh's fixed first wait of 120 s.

Decision (owner, 2026-11-13): 256 start positions stay, the same on every board; the default time limit of run.sh goes from 300 to 600 polls (at least 2.5 h), so the slowest configuration (about 1.7 h) fits.
