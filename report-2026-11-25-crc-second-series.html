CRC: the second board series (the boards' CRC hardware, tables in RAM)

The second series of the CRC kind measured two things the first did not. One is the boards' CRC hardware, driven by our code: the STM32 CRC unit on the NUCLEO-G474RE, NUCLEO-G0B1RE and NUCLEO-H723ZG, and the RP2350's DMA sniffer on the Pico 2. The other is the fifteen configurations with a table in flash, with that table copied to RAM by the image at start. It was decided on 2026-11-25 (change log), planned and counted in lab/plans/2026-11-25-crc-hw-and-ram-series.md, and run on 2026-11-25 from 11:45 to 21:58 UTC. Every number below is computed from the records under records/crc; every record was rebuilt from its commit and matched (kinds/crc/bench/crcverify.sh).

What was measured

  • 18 new configurations (kinds/crc/configs.txt, after "# The second series"):
    • adapter_hw_crc32, adapter_hw_crc16 and adapter_hw_crc8 (kinds/crc/adapter_hw.c), built only for the boards that have the unit (kinds/crc/boards.txt). The RP2350's sniffer has no CRC-8 mode, and the SAM D20's DSU and the nRF5340 are left out (the plan says why).
    • Fifteen *_ram configurations, one per configuration whose table lies in flash. The table's section is renamed from .rodata.* to .data.* in a copy of the library's archive (kinds/crc/bench/onecrc.py, ram_archive), so the image's start-up code copies it to RAM. The build checks that every table symbol lies once in RAM (kinds/crc/ramtables.txt, ram_check).
  • The same method as the first series: 8 placements, 2 passes, 24 scenarios of 256 calls, the reference timed in the same image, the method frozen at crc-method-freeze except the changes listed in the decision.
  • The 160 images per board of the first series rebuild byte for byte from the second series' tree (VL_TREE=1 crcverify, 20 of 20 per board), so the first series' records stand beside the new ones.

The two reruns

The NUCLEO-G0B1RE's hardware rows (a defect in our adapter).

  • The first run (04a2197) gave 25.5 cycles per byte with the cache on. That is slower than several tables on the same board (crcany's slicing by 4 with its table in RAM: 10.25), with errors 0: the values were right, the time was not the unit's.
  • The cause: the adapter's word loop copies each word with __builtin_memcpy(&w, p, 4). On the Cortex-M0+, which has no unaligned loads, gcc -O2 could not assume p aligned (the loop aligns it first). So it called newlib's memcpy for every word (bl memcpy in the image).
  • The fix: commit 40f1958 adds __builtin_assume_aligned(p, 4). On the M4 the code is the same as before.
  • The rerun: 2.00 cycles per byte with the cache on.
  • The first run's files are kept as superseded and make no record.
  • A scan of every image of all six boards (functions reachable from the timed call, looking for library helpers) found no second case in our code.

The NUCLEO-H723ZG (an option bit found set).

  • What was found: the board came back from other use with unknown software on it. FLASH_OPTSR2_CUR read 0x00000004, that is CPUFREQ_BOOST = 1; its factory value is 0 (RM0468 Rev 3, table 18 "Option byte organization"). The other option registers were at their factory values. The first series recorded no option bytes, so it is not known whether the bit was set then.
  • The decision: the owner decided that measurements made with wrong settings are made again.
  • Setting it back: the bit was set back to 0 through the probe (RM0468 §4.4.3: unlock, OPTSR2_PRG = 0, OPTSTART, OPT_BUSY clear, OPTLOCK). Every _CUR register was read before, after, and after a power cycle; RDP was never written.
  • The rerun with the bit at 0: all 864 means (18 configurations, 24 scenarios, results and baseline) are identical to the run with the bit at 1.
  • What follows: at the images' 64 MHz the bit changes no number. The run with the bit set is kept as superseded and makes no record.

The boards that came back

The NUCLEO-H723ZG, the Pico 2 and the nRF5340 DK had unknown software put on them while away. The series takes as ours only what it wrote. The first series' bundles on these three boards are treated as gone, which matters only for a rerun of the first series.

  • nRF5340 DK: locked, then erased.
    • What happened: the first write found the application core's debug port locked. probe-rs offered to erase the chip and was not allowed to. The port stayed locked after a power cycle.
    • Why it can lock: the port opens only when UICR.APPROTECT is Unprotected and firmware writes CTRL-AP.APPROTECT.DISABLE after each reset (nRF5340 Product Specification v1.6, §8.2 "Access port protection"). Our boot stub runs no image after a power-on, so nothing opens it. Whether that or the other software locked this board is not known.
    • The erase: one CTRL-AP ERASEALL of the application core (probe-rs ... --allow-erase-all, one command). probe-rs then wrote both UICR words to 0x50FA50FA itself.
    • Then: bundle 27 was written with no reset before it, and the first image opened the port. UICR and the results block were read back after the smoke.
    • Not touched: the network core. It is held in Force-OFF after every application-core reset and our firmware never releases it (§4.10.7), so it cannot run during a measurement.
  • NUCLEO-H723ZG:
    • the option bit above;
    • the boot region read back as the build's boot.bin.
  • Pico 2: the OTP read back raw.
    • The critical flags, the boot configuration page and the boot keys are all unprogrammed (0).
    • Lock words are set only for pages 0, 1, 2, 62 and 63, the defaults of a blank device (RP2350 datasheet RP-008373-DS-2, §13.4 and §13.5).

The baseline against the first series

The baseline (the bitwise reference, timed in every image) is the same code in both series. Its means in this series are identical to the first series' on every board, in all 72 scenarios (24 per CRC, three CRCs), to the third decimal. This holds also on the three boards that came back.

Retries

A run whose image has not finished at the first look is repeated with twice the wait (kinds/crc/bench/run-crc.py). The wait is kept per configuration, so a retry comes at the first image of a configuration that a run reaches.

  • Every retry of this series is of that kind: at p0, or at p4 where the H723 rerun reached a configuration first in bundle 28.
  • The H723's two series runs today had 14 each, 10 after 5 s and 4 after 10 s; the first series had 18 in 320 runs.
  • The logs show which images were retried and after which wait. They do not show why one configuration needs more than 5 s and another does not; that is not explained here.

The hardware rows

What a hardware row is:

  • The board's CRC unit, driven by our code (kinds/crc/adapter_hw.c); not a library.
  • The STM32 unit: the clock is enabled once, then CR, POL and INIT are set. The message is fed as bytes up to a word boundary, then words with their bytes swapped, then the last bytes. For CRC-32 the unit has no final XOR, so our code XORs the result with 0xFFFFFFFF.
  • The RP2350: a DMA transfer of the message to a dummy byte, with the sniffer computing CRC-32 or CRC-16 on the way.

What the tables show, as facts of these runs:

  • With the cache off, the table in RAM is lower on 79 of the 90 board-and-configuration pairs. The other 11 are the same (overlapping ranges): 8 on the H723, whose cache-off ranges are wide, 2 on the G0B1 and 1 on the G474.
  • With the cache on, it differs by board:
    • NUCLEO-G0B1RE and SAM D20: lower in all 15.
    • NUCLEO-G474RE: lower in 10, the same in 5 (the tables of 16).
    • nRF5340: lower in 9, the same in 6.
    • Pico 2: lower in 7, the same in 8.
    • NUCLEO-H723ZG: the same in all 15.
  • No configuration is higher with its table in RAM, on any board, with the cache on or off.
  • Bytes: a table copied to RAM still costs its bytes in flash (the initial values the start-up code copies) and the same number of bytes of RAM. The code is the library's own, unchanged.

zlib's division on the Cortex-M0+ boards

zlib's crc32_z divides once per call, before its braided loop: blks = len / (N * W) (crc32.c line 653, zlib v1.4). On the Cortex-M0+ (NUCLEO-G0B1RE, SAM D20), which has no divide instruction, gcc calls libgcc's __aeabi_uidivmod / __udivsi3 for it. This holds in both zlib configurations, in flash and in RAM.

So zlib's rows on those two boards include one library division per call. That is what a zlib user on these cores gets, not a fault of the method. The scan above found no other helper call in any timed function.

What is not explained

  • Why a configuration needs more than the first wait of 5 s at its first image (the retries above).
  • The NUCLEO-H723ZG with the cache off:
    • its per-byte ranges are wide for the tables in RAM as for those in flash (e.g. ETL's table of 256 for CRC-8: 15.04–34.00 in flash, 5.00–25.00 in RAM);
    • with the cache on, the RAM and flash rows are the same.
    • The board's data cache and its 7 flash wait states at 64 MHz (see the method) fit both, but neither was measured.
  • The Pico 2's hardware rows with the cache off: the fixed cost of a 16-byte call (764–1081 cycles) against 1.18–1.38 per byte.
  • The G474's tables of 16: they are the same in RAM and flash with the cache on, while its tables of 256 are lower in RAM.
