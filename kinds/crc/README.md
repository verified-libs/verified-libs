# CRC calculation: the second kind (host work)

CRC calculation in software, chosen after a survey of what carries over
from the ring buffers.

**Status: the first board series is done** (step 10, commit `6301058`,
2026-11-24 to 2026-11-25, six boards, 120 records in
[`records/crc`](../../records/README.md)); its numbers are on the
[results page](../../site/content/results-crc.md) and how they were made on
the [method page](../../site/content/method-crc.md). The numbers of steps 1
to 9 come from host runs and cross builds, made to plan that series; they
are not results about a library on a board.

Everything of this kind lives in `kinds/crc/`, outside `firmware/`: a file under
`firmware/` would stop the export of every ring-buffer record.

## Step 1: the interface and the reference

- [`crc.h`](crc.h): the adapter interface. One adapter is one library, one
  CRC and one implementation of it. The one-shot call has the signature of
  the ring-buffer benchmark's operations, so the boards' `time_call` times
  it unchanged. Its comment gives the reasons.
- [`ref_crc.c`](ref_crc.c): the reference, the bitwise algorithm written
  from the parameters of the [CRC RevEng catalogue](https://reveng.sourceforge.io/crc-catalogue/all.htm)
  for CRC-32/ISO-HDLC, CRC-16/IBM-3740 and CRC-8/SMBUS. It is also the
  baseline of the benchmark. The reflected polynomial and initial value
  are constants of the build, each checked at compile time against the
  value the literature gives (`_Static_assert`).

The reference is checked three ways ([`ref_check.c`](ref_check.c),
[`ref_check.py`](ref_check.py), `bash run.sh refcheck`): the catalogue's
check value and residue, a second implementation that is not ours
(Python's `zlib.crc32` and `binascii.crc_hqx`, for CRC-32 and CRC-16), and
four builds of the reference with one parameter wrong, each of which must
be caught. Run on 2026-11-24 (toolchain image 2026-11-13):

The residue does not depend on the initial value, and the CRC-8 residue
is 0 for every wrong polynomial and reflection tried; the check value
catches every wrong build. Python's standard library has no CRC-8, so
CRC-8/SMBUS has two of the three checks.

## Step 3: the host test, and that it can fail

[`test_crc.c`](test_crc.c), run by `bash run.sh test` in the toolchain
image, checks every configuration against the reference:

- **check**: the catalogue's check value, the CRC of "123456789";
- **lengths**: every length from 0 to 300 bytes at every start alignment
  from 0 to 7, random bytes with fixed seeds; each message lies at the end
  of a buffer of its own from `malloc`, so a read past its last byte is
  seen in the sanitizer build;
- **splits**: every length from 0 to 300 cut at every point into two
  `update` calls, and the same with an empty `update` between them;
- **step**: every input of one step of the CRC. Over all messages of w/8
  bytes the register takes every value exactly once (the test checks this
  for the reference first), so all messages of w/8 + 1 bytes give every
  pair (state, byte) of the last step exactly once: all 2^16 messages of
  2 bytes for CRC-8, all 2^24 of 3 bytes for CRC-16. For CRC-32 that would
  be 2^40; the test runs every last byte after 65536 random states
  (marked `*`), and the proof for every state is in step 3b below.

The test is built twice, plain at `-O2` and with the address and
undefined-behaviour sanitizers, and both must exit 0. Five deliberately
broken adapters of ours ([`adapters_broken.c`](adapters_broken.c)) must
each fail the check made for its fault. The Rust adapter's own test (the
check value, in one call and in two parts) also runs under Miri
(`make miri`).

zlib is in the test twice. Its braided code takes 8-byte words on the host
(x86-64) and 4-byte words on the boards (`crc32.c`: W is 8 on x86-64 and
AArch64, 4 elsewhere), each word size with a loop and tables of its own, so
the host's own build runs neither the loop nor the tables the boards run.
The second row is the same `crc32.c` built with the library's own
`Z_TESTW=4`, 4-byte words as on the boards (and with its `Z_PREFIX`, so
both builds link into one program). `make test` first checks the size of
the braid table in both objects: 4096 bytes for 4-byte words, as in the
boards' images, and 8192 for 8-byte words. Tried once by hand: with one
bit of that 4096-byte table changed in the object file, the second row
fails "lengths" (first at length 52) and "splits", and the first row
still passes.

## Step 3b: CRC-32 for every input (CBMC)

For CRC-8 and CRC-16 the host test above runs every input of a step. For
CRC-32 it cannot (2^40 pairs), so [`proof/harness.c`](proof/harness.c) has
CBMC prove, for one configuration of each class, that the library's result
equals the reference's for **every** previous CRC value and **every**
message of `MSG_LEN` bytes (each byte and the CRC value nondeterministic).
The sources are preprocessed by the boards' compiler (`arm-none-eabi-gcc`,
Cortex-M4, newlib) and checked with CBMC's ARM data model, at most 60
minutes each, four at a time ([`proof/run.sh`](proof/run.sh), `make
proof`). A control with a fault at one input in 2^40 must fail, to show
that the proof does cover every input.

crcany's slicing by 4 (`_word`) did not finish this way: three runs (4
and 8 bytes, offsets 0 and 1) each stopped at the 60 minutes. Its step
takes four table lookups and XORs them, which is hard for a SAT solver;
CaDiCaL, Glucose and MiniSat took the same time on the 8-byte table proof
(46 to 47 s), so another solver was no way out. The one 4-byte step is
proven in two parts instead ([`proof/word_lemma.c`](proof/word_lemma.c),
[`proof/word_exhaustive.c`](proof/word_exhaustive.c)):

1. CBMC: the library's result for a previous CRC `c` and an aligned word
   `w` depends only on `c ^ w`, `word(c, w) == word(c ^ w, 0)`, and the
   same holds for the reference;
2. every one of the 2^32 values `x`: `word(x, 0) == ref(x, 0)`, computed,
   not sampled.

Together: `word(c, w) = word(c ^ w, 0) = ref(c ^ w, 0) = ref(c, w)` for
all 2^64 pairs. Both parts have a control that must fail. Part 2 is
compiled by the host's gcc (x86-64), not by the boards' compiler; both are
little-endian with 32-bit `uint32_t`, and the code is plain C.

zlib's braided loop, which a message reaches from 40 bytes at a word
boundary, did not finish as one proof either (below). It is proven in parts
for 40 and 60 bytes at offset 0
([`proof/`](proof/)). Over GF(2) a CRC is an affine function of its input bits (the start
value and the message): linear but for a constant. Two affine functions that
agree at the zero input and at every input with exactly one bit set agree
everywhere; for 40 bytes that is 1 + 352 inputs instead of 2^352. For
`x = (c, w0 ... w9)`, `c` the start value and `w` the message words:

| part | what | how |
|---|---|---|
| A | `crc32(c, w, 40)`, the call of the adapter and of part D, equals a formula F(x) written with zlib's own tables: XOR, the complement of `c`, `braid()` and `crc_word()` ([`proof/braid_formula.c`](proof/braid_formula.c)) | CBMC, every x |
| B | `braid()`, `crc_word()` and S, the reference over four zero bytes, are linear: f(x) is the XOR of f at the set bits of x ([`proof/braid_linear.c`](proof/braid_linear.c)) | computed on the host, all 2^32 values of each |
| C | the reference over 40 bytes is `S(...S(S(r ^ w0) ^ w1)... ^ w9)` ([`proof/braid_ref.c`](proof/braid_ref.c)) | CBMC, every r and w |
| D | zlib equals the reference at x = 0 and at each of the 352 inputs with one bit set ([`proof/braid_onehot.c`](proof/braid_onehot.c)) | CBMC, 353 inputs |
| E | A and B make zlib's side affine, C and B the reference's; with D they are the same function | argued, not machine-checked |
| F | the typedefs of `z_crc_t` and `z_word_t`, the initialisers of `crc_table` and `crc_braid_table` and the body of `crc_word()` are the same text as preprocessed for part B (host, `-DZ_TESTW=4`) and for parts A and D (the boards' compiler) | text comparison |

`braid()` is the four lookups in `crc_braid_table` that the loop makes for
one word; A and B use the one text of it in
[`proof/braid.h`](proof/braid.h). The same is done for 60 bytes (three blocks, so the loop runs twice; 1 + 512
inputs in D). Each of A, B, C and D has a control with one wrong value that
must fail. Part E in full: by A, zlib's result is F(x), a composition of
XOR, the complement of `c` (XOR with a constant) and the functions `braid()`
and `crc_word()`; by B these two are linear, so F, and zlib's result, is
affine in x. By C, the reference's result is a composition of XOR, its
fixed start and final XOR (constants) and S, which is linear by B, so it is
affine in x too. An affine function g is g(0) XOR a linear part, and the
linear part is fixed by its values at the single bits; by D the two sides
agree at 0 and at every single bit, so they are the same function of x.
What no tool checked: this step from "affine and equal at 353 (or 513)
inputs" to "equal"; and that the host's compiler (part B) and CBMC's ARM
model (parts A, C and D) give unsigned 32-bit arithmetic the same meaning.
The texts the two compute with are the same: part F covers zlib's tables,
`crc_word()` and its types, `braid()` is one file, and S is the
reference's own C (`ref_crc.c`), compiled by both.

What is proven and what is argued, apart:

- **Proven**: crcany's table of 256 (`_byte`), Zephyr's table of 16 and
  crcany's bitwise code: every message of the length given from every
  state. For one byte that is the whole byte step of the inner loop.
  crcany's slicing by 4: the whole 4-byte step, in the two parts above.
- **Proven of zlib, and what is not**: every message of 24 bytes at
  offsets 0 and 1 from every state. That takes the braided branch (it
  starts at 23 bytes: five braids of 4-byte words on a 32-bit core,
  `N * W + W - 1` in `crc32.c`), but 24 bytes hold one block of five
  words, and the loop over the blocks before the last (`while (--blks)`)
  does not run for one block. So the proof covers the bytes before the
  first word boundary, the last block, where the five braids are
  combined (`crc_word()`, with the byte table `crc_table`), and the bytes
  after it. This proof does not cover the loop over the earlier blocks and its
  tables (`crc_braid_table`), which a message reaches from 40 bytes at a
  word boundary. That loop is proven in parts for 40 and 60 bytes (next
  point) and tested for the rest: the host test's second
  zlib row (step 3) runs it with the boards' 4-byte words for every
  length to 300 at every alignment, in both builds.
  One try to prove it, 40 bytes at offset 0 (two blocks, so the loop
  runs once; the same harness, `--unwind 42`), did not finish within
  60 minutes on 2026-11-24 and is not in `run.sh`.
- **Proven in parts of zlib**: every message of 40 and of 60 bytes at
  offset 0 from every start value, so the loop over the earlier blocks
  and `crc_braid_table` once and twice: parts A, C and D by CBMC, part B
  computed for all 2^32 values, part F a text comparison, part E argued
  (above). Other lengths from 40 bytes on, other offsets and other word
  sizes stay tested, not proven.
- **The controls** fail as they must, each at its one wrong input, so the
  proofs above do cover every input.
- **Argued** (by reading the code, not proven): that a longer message is
  the same step repeated, so the equality of one step carries over to
  every length. For crcany's slicing by 4 also that the bytes before the
  first aligned word and after the last are handled by the byte step of
  the same table as `_byte` (`table_byte` is `table_word[0]`), which is
  proven. The host test checks every length to 300 at every alignment,
  and the 8-byte proofs check that steps compose.
- **Not covered by a proof**: the CRC-32 configurations that are C++ or
  Rust (ETL, the crc crate) and libcrc's run-time table; for them the
  CRC-32 step is tested on all 256 bytes from 65536 random states, not
  proven.

## Step 4: cross builds and sizes

[`cross.sh`](cross.sh) (`make cross`) compiles every configuration and the
reference for Cortex-M0+, M4, M7 and M33 at `-Os` and `-O2`, with the

What the table shows, as facts of these builds:

- The same class can cost very different flash: crcany's byte routine
  keeps its four word tables in one array (`table_byte` is
  `table_word[0]`), so its CRC-32 table of 256 costs 4096 bytes where
  ETL's costs 1024; its CRC-8 byte table costs 1024 where ETL's and
  AceCRC's cost 256.
- libcrc and CRC++ build their table in RAM at run time (1025 and 524
  bytes of RAM, no table in flash).
- zlib's CRC-32 adds 5120 bytes of tables and 700 to 1100 bytes of code.

### Is the result one per library, or one per algorithm?

[`loops.py`](loops.py) disassembles every configuration's work loop
(`arm-none-eabi-objdump`) and compares the instructions one iteration
executes, for every pair of configurations with the same CRC and class,
on every core and level. "Same opcodes" means the same instructions in
the same order, where an operand may differ (the order of a compare's
operands, which register counts); "same" means identical up to register
names. Over all pairs and builds: on M4, M7 and M33, 57 of 108 are same or
same opcodes; on M0+, 13 of 36.

| Pair (same class) | M4, M7, M33 (-Os, -O2) | M0+ |
|---|---|---|
| CRC-32 table of 256: ETL, crcany, libcrc (each pair) | same opcodes, 8 instructions per byte at -Os, 7 at -O2 | differ in most builds |
| CRC-32 table of 256: the crc crate (Rust) with any of them | differ: a down-counter (7 per byte at -Os), unrolled at -O2 | differ |
| CRC-32 table of 16: ETL and Zephyr | same opcodes in 5 of 6 builds | same at -O2 |
| CRC-16 table of 256: crcany and libcrc | same opcodes | same opcodes |
| CRC-16 table of 256: ETL with crcany or libcrc | same opcodes at -O2 on M7 and M33, else differ (at -Os on the M4: `eor.w` against `eors`) | differ |
| CRC-16 table of 256: CRC++ with any | differ | differ |
| CRC-8 table of 256: ETL, crcany, AceCRC (each pair) | same opcodes | same or same opcodes |
| CRC-8 table of 16: ETL and Zephyr | differ (15 or 16 against 14 or 15 per byte) | differ |
| CRC-32 bitwise: crcany and ours | same (5 instructions per bit) | same (9 per bit) |

So on the Armv7-M and Armv8-M cores the C and C++ byte-table code of
three or four libraries compiles to the same instructions per byte; the
Rust crate, CRC++ and the tables of 16 for CRC-8 do not. Same
instructions are not yet the same cycles: libcrc reads its table from
RAM where ETL and crcany read theirs from flash, and crcany's table is
four times the size, which matters where a cache holds only part of it
(the [series proposal](../../reports/2026-11-25-crc-first-series.md)).
Whether same opcodes give the same cycles is what a first board series
would show.

**The kind's segments.** The kinds share one numbering of segments, so a
bundle number names one bundle; each kind has a range of 100. The ring
buffers' table holds segments 0 to 19, with room for one more configuration
in them (12 free slots of 12 KB), and grows upwards from there. This kind's
first segment was 20, the next free one, until 2026-11-24; it is 100 now, so
that more ring buffers do not run into it. No series had been run. 80 is a
multiple of every board's segments per bundle, so nothing but the numbers
changed: built before and after, all 960 images have the same address and
the same bytes, and each of the 26 bundles has the same loaded segments
(the bundle files differ: their symbol names carry the bundle's number). A
board holds one bundle at a time, of either kind; a bundle of this kind
takes the place of a ring-buffer bundle as another ring-buffer bundle would.

**Where the placement bytes lie.** In version 2's ring-buffer images they
lie behind the adapter, with the FAR bytes: the adapter stays and the
library moves. Seven of this kind's configurations are libraries of headers
(ETL's six and CRC++), whose loop is compiled into the adapter: there only
the table would move, and the loop would lie at the same address in all
eight placements, while the loop of a library with source files of its own
would move. So in this kind the placement bytes lie before the adapter:
adapter and library move together, by the same bytes, in all 20
configurations, and the distance between them is FAR in every image
(`nm` of the NUCLEO-G474RE images of ETL `crc32_t256`: the loop 0 and 12
bytes behind the fixed part at placements 0 and 12, the table 12 bytes
further too). The fixed part, the image sizes and the slots are as before
the change. One exception, printed above: rustc aligns the `crc` crate's
functions to 8 bytes for the Cortex-M7 (`readelf -S`: `.text.*` of the
crate's archive, alignment 8), so on the NUCLEO-H723ZG that code takes
four positions of a 32-byte line in the eight placements, not eight.

## Step 9: before the series

Made on 2026-11-24 after a review of step 8, so that the files a record is held against do not change after
the series: a change under `kinds/crc` would stop the export of every CRC
record, as there was no rebuild ledger for the kind then (there is one
since 2026-11-24). No board was used.

- **The record writer** takes a run file only if it is of the build next to
  it (the same commit, toolchain image and board), if its two result sets
  are the baseline and the configuration it names, and if both agreed with
  the reference on every call; every field it compares must be in every run
  (a field missing in all of them was taken as equal before); and the passes
  must be exactly 1 and 2, those of a series, so a smoke run of one pass
  never becomes a record. One test case each; 15 of 15 as expected.
- **The check of a record** (`crcverify.sh`) counts an error of its
  comparing program as "could not be checked" (exit 2), not as "differs".
- **The Pico 2** is written in parts: in this lab, about 65 s after a flash
  write starts, the host's hub power-cycles the board's own USB port, which
  cannot answer while the probe writes. `run-crc.py` writes a Pico 2 bundle
  of more than 250 units of 4096 bytes in parts of whole segments of at
  most 250 units (Intel HEX files, 25 to 30 s each), waits between parts
  until the board answers, and then compares the whole bundle with the
  flash. It counts as one write. Tried without a board, with a stand-in for
  probe-rs: the bundle of 505 units in three parts (250, 249 and 6 units),
  the bytes written equal to the bundle's loadable bytes.
- **The Pico 2's XIP cache at a start**: an image measures with the XIP
  cache off, then on (`board_cache()`), and the switch (XIP_CTRL, EN) keeps
  its value over the reset the runner uses (SYSRESETREQ): read over the
  probe, 0x80 before and after a reset with the cache off, 0x83 with it on.
  A run that is looked at before it has finished (a wait too short, then
  doubled) can so leave the cache off for the next start, which then runs
  its start-up with the cache off: in the smoke test of 2026-11-24 a run
  of about 30 s was not finished after 40 s, and the run that finished
  (80 s) had an empty call of 275 cycles where every other run had 5; its
  means were those of the other pass, as every scenario sets the cache
  itself, but the record writer refused the configuration (the runs differ
  in `empty_call_raw_min`). `run-crc.py` now switches the cache on over
  the probe before every reset of the Pico 2, the state a finished run
  leaves.
- **A repeat on your own board**: [`repeat.sh`](repeat.sh), as the
  repository's `repeat.sh` for version 2: it finds the board as that one
  does, builds the images of the tree, runs them (two passes; quick: up to
  three configurations of one bundle, full: every bundle), makes records and
  compares them with ours by [`bench/crccompare.py`](bench/crccompare.py)
  (images by their bytes in flash and address; every mean of the
  configuration and of the baseline, 1 % or 0.05 cycles, against one of our
  passes). The comparison was tried on made-up records (the same: exit 0;
  one mean 14 % slower: exit 1, that mean named; run files instead of
  records: exit 2).

**A table in RAM.** The library is built as for its row in flash. Then
[`bench/onecrc.py`](bench/onecrc.py) (`ram_archive`) renames the section
of each table symbol named in [`ramtables.txt`](ramtables.txt) from
`.rodata.*` to `.data.*` in a copy of the archive. The image's start-up
code copies `.data` from flash to RAM before `main`, as for any
initialised variable, and the build checks that every table symbol lies
once in RAM (`ram_check`). The code is the library's own, unchanged:
- the table's bytes stay in flash, as the initial values the start-up
  code copies, and the same number lie in RAM;
- the sizes of step 4 hold with the table counted twice: in flash as
  before, and in RAM.

The table symbols in RAM, read from the board images (`nm`, NUCLEO-G474RE),
are as large as step 4's tables in flash:
- 1024 (ETL CRC-32), 4096 (crcany CRC-32 byte and word), 1028 (Rust);
- 64 (ETL and Zephyr tables of 16, CRC-32), 5120 (zlib: `crc_table` and
  `crc_braid_table`);
- 512 (ETL and crcany CRC-16), 32 (ETL CRC-16 table of 16);
- 256 (ETL and AceCRC CRC-8), 1024 (crcany CRC-8), 16 (ETL and Zephyr
  tables of 16, CRC-8).
