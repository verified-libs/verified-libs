Which memcpy the Rust libraries are measured with (2026-11-13)

The benchmark firmware is a C firmware: the Rust libraries are linked into it as a static library, and their calls to memcpy go to the C library's (newlib's, optimised for speed). A firmware written in Rust links Rust's own memory functions instead (compiler_builtins, as shipped in the rust-std archive for the target). MEMCPY=rust builds the benchmark that way, for the C code in the firmware too, so the two can be compared. Rust and multi-producer sets, -O2, code in flash, five boards (the Pico 2 was busy).

("64-byte copy alone" is the benchmark's baseline: one copy of 64 bytes and nothing else.)

  • Rust's memcpy is the slower one here, by more than a factor of two for a 64-byte copy on the M33, M4 and M7, and by 20 to 30 % on the M0+ boards. The two libraries that copy blocks with it, bbqueue and embassy-sync Pipe, need up to 1.8 times the cycles per byte for a 64-byte block on the M4 and M33, about 1.4 times on the M7, and almost the same on the M0+.
  • embassy-sync Pipe calls memcpy for a single byte too, so its one-byte write and read slow down by 80 to 90 cycles on the M33 and M4, 20 on the M7 and about 15 on the M0+.
  • heapless is not affected: its queues move one element at a time without memcpy (all means equal, except on the H723, where the one-byte means of heapless spsc::Queue moved from 40 / 35 to 34 / 29 cycles: the other memory functions shift the code, a placement effect).
  • The C++ configuration in the same firmwares that calls memcpy, DNedic lockfree spsc::RingBuf, slows down in the same way (G474: 98 → 146 cycles for one byte, 3.9 → 10.2 per byte for a block), which shows that the difference is the memory function and not the libraries.

What it means for the comparison page: its numbers for bbqueue and embassy-sync Pipe are with the C library's memcpy, the favourable case for them. In a pure Rust firmware built with the stock rust-std they would be slower by the amounts above, unless the project links another memcpy. The page does not show the MEMCPY=rust numbers; whether it should (as a second figure for the Rust libraries) is open.

Records: *-rb-bench-rust-flash-memcpyrust-* and *-rb-bench-mp-flash-memcpyrust-* of 2026-11-13 (commits 9518bf8 and 8e9fcd5; the change between them does not touch the benchmark firmware), compared with the records of the same sets with the default memcpy.
