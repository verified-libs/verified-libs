  • The negative control was caught in every run.

  • 1.4.0: single-byte pop 31 → 20 cycles, but 64-byte blocks became 2.2× slower from flash and 3× slower from SRAM.
  • 1.4.1: keeps the single-byte pop and is the fastest of the three versions at 16 and 64 bytes.
  • At 4 bytes 1.4.1 sits between the two, about 13 cycles slower than 1.4.0.
  • Flash: 1.4.0 is the smallest version. 1.4.1 links newlib's memcpy again, as 1.3.2 did:
  • 236 B of the difference is that memcpy. Any program that already uses memcpy pays it anyway.
  • The other +94 B is the copy logic in push_n/pop_n.

Why: which memcpy gets linked

pxq 1.4.0 (commit 093e81e) replaced memcpy in push_n/pop_n with element loops. The commit says "newlib-nano memcpy is a byte loop too", measured on an STM32G071 (Cortex-M0+). Whether that holds depends on how the C library was built. The core does not decide it:

Toolchain memcpy in libc / libc_nano Source
Ubuntu libnewlib-arm-none-eabi 4.6.0 (ours), Cortex-M33 multilib 236 B, copies words disassembled here
Ubuntu newlib 4.6.0, Cortex-M0+ multilib 168 B (not disassembled) nm here
STM32CubeIDE 1.13.2, GNU Tools for STM32 11.3, newlib 4.2.0 memcpy-stub, a byte loop: 18 B (M0+), 28 B (M4/M7), 26 B (M33) checked by the owner, not repeated here

With our toolchain, the M33 memcpy handles 8 bytes or more like this: if the source or the destination is word-aligned, it goes straight to a word loop and lets the other side be unaligned. The M33 handles unaligned word access in hardware, which an M0+ could not do. If neither side is aligned, it first copies 1–3 bytes to align the destination. Below 8 bytes it is a byte loop. That is why the inline loop of 1.4.0 wins at 4 bytes but loses from 16 bytes up, and why 1.4.1's threshold of 8 bytes fits this library. With ST's toolchain, memcpy is a byte loop at every size. There, 1.4.0's inline loop is expected to be at least as fast as 1.3.2 at every size, but that has not been measured.

How the benchmark lays out the copies: the block scenarios start one slot into the ring (scen_block pushes and pops one byte first). The ring side of every copy is therefore at address ≡ 1 mod 4, and the user buffer is word-aligned. Every second 64-byte transfer is split at the wrap (63 + 1 bytes). memcpy was measured in this less favourable case. With both sides aligned it would avoid unaligned accesses, but that is not measured.

Limits

  • One board and one core. The byte-loop memcpy case is measured with newlib's stub on this M33 (addendum), not with ST's toolchain itself.
  • 0 errors over these runs makes hidden ordering bugs unlikely for these configurations. It does not prove their absence.
  • pxq is the owner's library. Its numbers need an independent repetition before they count (principle 6).

Follow-ups

  • Repeat on the Cortex-M0+ (NUCLEO-G0B1RE, on order), with both toolchains.

With a byte-loop memcpy the order reverses: 1.4.0's element loop is the fastest from 16 bytes up, and 1.4.1 inherits the byte loop above 8 bytes. 1.4.0 measures the same as with the word-copying memcpy (465 / 402 against 466 / 403), as expected since it does not call memcpy. So which version is faster depends on the C library, not only on pxq.
