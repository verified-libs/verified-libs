# Plan: CRC in software as the second kind (host work, one night)

Written 2026-11-24, after the owner chose the order from the
[comparison of kinds](../../reports/2026-11-24-next-kind.md): **D (CRC
calculation in software) first, then A (fixed-block pools) in a narrower
form.** The reasons are in the report's "Decision" section.

This plan is the work of one unattended night on the host. It ends with
a kind that is ready for the owner's decision on a first board series,
not with a series, and with nothing public.

Read first: the [CRC survey](../../candidates/crc-embedded.md) (the
candidates, the three CRCs, the table of boards), the
[step-1 report](../../reports/2026-11-24-what-carries-over.md) (what is
general, what the export check holds), and the
[pool pilot](../../pilot/pools/README.md) (the shape of a host pilot:
lock file, fetch script, run script, a test shown to fail).

## What the night must give

In the morning the owner can decide on a first board series for CRC from
facts, not guesses:

- an adapter interface and a reference whose correctness is shown;
- a first set of configurations, pinned, built for the host and for the
  four cores of the six boards;
- a host test that proves each configuration against the reference and
  is shown to fail on broken ones;
- the bytes of code and table per configuration and core;
- one benchmark image for one board, built and not flashed;
- a **counted** proposal for the first series: images, segments, flash
  writes per board.

It must also answer, as far as the host can, the open question of the
review: **is the result one per library, or one per algorithm?** If two
libraries with the same algorithm compile to the same loop, the page for
this kind compares algorithms on boards and names the libraries that
offer each, which is a different page from the ring-buffer one.

## Rules for this night

The standing rules of the lab apply, and the night rules of the
[previous plan](2026-11-24-next-library-kinds.md) ("Rules for this
night") apply word for word: nothing outward, no board and no flash
write, the frozen files stay untouched, public texts are facts with a
source, a possible defect goes to `lab/drafts` only and the work on that
library stops, downloaded code is untrusted, questions for the owner go
at the end of this file. In addition:

- **Branch and place.** Branch `kind-crc` from `main` (which holds
  `next-kind` since 2026-11-24), in its own worktree
  (`git worktree add ~/vl-wt-crc -b kind-crc origin/main`). Commit and push after each step. No attribution lines in
  commits.
- **Everything of this kind lives in `kinds/crc/`**, a new top-level
  directory. Nothing is added or changed under `firmware/`: a file
  there stops the export of all 265 ring-buffer records, a file outside
  does not (tested twice on 2026-11-24). After every commit
  `python3 lab/tools/public-export.py --check` must still say "0 records
  that cannot be rebuilt".
- **`lab/tools/public-export.py` is not changed this night.** The night
  writes a proposal for how it holds a second kind (step 6); the change
  is the owner's decision and is made in the daytime.
- **Licences** are taken from each repository's licence file, read
  again for every library that is pinned (the owner's answer of
  2026-11-24); the GitHub API is not used.
- **Libraries**: pinned by commit in `kinds/crc/libs.lock` (the format
  of `pilot/pools/libs.lock`), fetched by a script into
  `~/vl-next/kind-crc/<name>`, compiled and run only inside the
  toolchain image `verified-libs/toolchain:2026-11-13`.
- **Code generators** (crcany, pycrc) run only inside the container. The
  generated C is not committed: the build generates it from the pinned
  generator, and the lock file records the command line and the SHA-256
  of the output.
- **A value that differs from the reference** is first our own fault
  until shown otherwise: check the parameters against the catalogue and
  the adapter against the library's documentation. If it stands, it is a
  possible defect: `lab/drafts` only, named in the morning status, and
  the work on that library stops.
- **No number of this night is a result.** Sizes and counts go in
  `kinds/crc/README.md`, marked as provisional. Nothing is written under
  `records/` or `site/data/`.
- Every wait has a hard timeout. A proof attempt (CBMC) gets at most 60
  minutes of wall time per configuration; if it does not finish, the
  text says so.

## Steps

1. **Interface and reference.**
   - `kinds/crc/crc.h`: one adapter per library, CRC and implementation:
     a name, the CRC (one of the three below), the class of algorithm
     (bitwise, table of 16, table of 256, slicing by N, other), `init`,
     and the one-shot call `crc(addr, len)` in the shape the boards'
     `time_call` takes (`uint32_t op(uintptr_t, uintptr_t)`). Where a
     library has a streaming interface, also `update` and `final`. The
     header's comment gives the reasons, as `pilot/pools/pool.h` does.
   - `kinds/crc/ref_crc.c`: the bitwise algorithm written from the
     catalogue's parameters (width, polynomial, initial value, input and
     output reflection, final XOR), for CRC-32/ISO-HDLC,
     CRC-16/IBM-3740 and CRC-8/SMBUS. It is the reference of the proof
     and the baseline of the benchmark.
   - The reference is itself checked three ways: the catalogue's check
     value and residue for each CRC; for CRC-32 and CRC-16 a second,
     independent implementation on random inputs (Python's `zlib.crc32`
     and `binascii.crc_hqx` inside the container); and a reference built
     with one parameter wrong must fail each of these.

2. **The first configurations: at most 20, each with its reason.**
   Written as a table in `kinds/crc/README.md` before any adapter is
   built. Constraints:
   - For each of the three CRCs, the same class of algorithm from at
     least two libraries (this is what answers the open question above).
   - CRC-32 also with a slicing or multi-word implementation (stbrumme
     slicing-by-4 or -8, zlib).
   - One Rust crate (`crc`), built as a static library with a C
     interface, as `firmware/rust-adapters` does for ring buffers.
   - Left for later, and said so: slicing-by-16, the boards' CRC
     hardware, libraries that need the Arduino core to build.
   A library that cannot be built alone within an hour is listed with
   the reason and replaced.

3. **The host test, and that it can fail.** `kinds/crc/test_crc.c`, run
   by `bash kinds/crc/run.sh test` in the container. Per configuration:
   - against the reference: every length from 0 to 300 bytes, every
     start alignment 0 to 7, random data with fixed seeds, and, where
     the library streams, every split of a message into two parts;
   - one step for every input: for CRC-8 all 2^8 × 2^8 and for CRC-16
     all 2^16 × 2^8 pairs of (state, byte);
   - for CRC-32, where 2^32 × 2^8 is too many: first CBMC (in the image)
     on the equivalence of one step for all inputs, for one
     configuration of each class; if that does not finish, the argument
     by linearity over GF(2), with what is proven and what is argued
     written apart;
   - the whole test also built with the address and undefined-behaviour
     sanitizers; Miri for the Rust adapter if it runs.
   Deliberately broken adapters, each of which must be caught by the
   check made for it: one wrong table entry; a wrong initial value; a
   missing final XOR; the last `len % 4` bytes skipped; the state not
   carried between two `update` calls. The test exits 0 only if every
   verdict is the expected one, and its output goes in the README as in
   the pool pilot.

4. **Cross builds and sizes.** Every configuration compiled for
   Cortex-M0+, M4F, M7 and M33 at `-Os` and `-O2`, with the compiler
   flags of the version 2 benchmark (read from
   `firmware/nrf5340-rb-bench/onebuild.sh`; that file is not changed).
   From the map file per configuration and core: bytes of code, bytes of
   table, and whether the table lands in flash or in RAM. Then the
   comparison the open question needs: for each pair of libraries with
   the same class of algorithm, is the inner loop the same instructions?
   (`objdump` of the two, compared; the text says which pairs are equal,
   which differ, and in what.)

5. **One benchmark image for one board, built and not flashed.**
   `kinds/crc/bench/`: its own `bench.h` defining the type `rb_op` that
   `firmware/common/<board>/board.h` includes, a harness with the
   scenarios (lengths 1, 4, 16, 64, 256 and 1024 bytes; buffer aligned
   and at offset 1; cache off and on; every result compared with the
   reference in the image), the reference as the baseline, and one
   configuration, linked for the NUCLEO-G474RE against the unchanged
   board support. The README gives the image's size and the shape of
   its result block. If the board support cannot be used without
   changing a file under `firmware/`, the step stops there and says
   what would have to change: that is a finding for the owner.

6. **The proposal for the first series, counted.** In
   `reports/2026-11-25-crc-first-series.md`:
   - from the real image sizes: images per board, segments of the slot
     table, and flash writes per board with the ring-buffer bundles left
     in place, with the SAM D20 (256 KB of flash) worked out on its own;
   - the table in flash and the table copied to RAM: how each is built,
     and what it adds in images;
   - per board, what "cache on" covers for a table read from flash,
     from the reference manuals (`~/vl-dev/datasheets` holds RM0440,
     RM0468 and the STM32H723 data sheet; the others from the vendors'
     public documentation, with links); what could not be found is named
     as unknown;
   - placement: whether eight placements of the code are needed at 1024
     bytes, and whether the table's own alignment is a new axis; how a
     small first run on one board would settle both;
   - the result of step 4's comparison and what it means for the page:
     one line per library, or one per algorithm with the libraries
     named;
   - the export check for a second kind, as a proposal only: the records
     of this kind in a directory of their own, their test sources
     `kinds/crc` plus `firmware/common` and the three lab files, the
     rule for ring-buffer records unchanged; and the three cases a test
     of the change must show (a file in `kinds/crc` leaves the
     ring-buffer records exportable; a file under `firmware/` still
     stops them; a change under `firmware/common` counts for both);
   - what the runner and the record tools need (copies with the result
     block's shape as a parameter), as a list, not as code.

Order: 1, 2, 3, then 4, 5, 6. Steps 1 to 3 get their full depth before
anything else; if the night is too short, the report of step 6 is
written from what there is and says what was not done.
