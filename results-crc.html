Results: CRC calculation

The results of one of the two kinds of library so far; the other is embedded ring buffers (all kinds, ring buffer results). The same numbers by CRC, board, message and cache, with every length and both starts: Compare.

Status: the kind's first and second board series. Every number comes from a record under records/crc that can be rebuilt and repeated from this repository (how). Numbers are facts about the pinned versions, the configuration and the board below, not general rankings.

Thirty-five configurations of eight libraries, for three CRCs of the CRC RevEng catalogue (CRC-32/ISO-HDLC, CRC-16/IBM-3740, CRC-8/SMBUS), on six boards. Twenty are the libraries as they ship. Fifteen are those of them whose table lies in flash, with the table copied to RAM by the image at start ("table in RAM"). The last row of a table, on the four boards that have one, is the board's CRC unit, driven by our code; it is not a library, and its name cell says so.

Every configuration was checked against a reference before it was timed, and every timed call's result was compared with the reference's on the board (method). Two series, two passes each: - the first, commit 6301058, 2026-11-24 to 2026-11-25 (report); - the second (tables in RAM and the boards' CRC units), commits 04a2197 and 40f1958, 2026-11-25 (report). Compiler: arm-none-eabi-gcc 14.2.1, -O2 -DNDEBUG, newlib-nano; the Rust crate with rustc 1.99.1 at the same optimisation level; pinned toolchain image. The libraries are fetched at the commits in kinds/crc/libs.lock, never copied into this repository.

How to read the tables

One table per board, CRC and cache setting: the cache on first, then off. One row per configuration, in the order of kinds/crc/configs.txt; the order is not a ranking. Each configuration's name links to its record.

  • Class and Table: the algorithm and where its table lies (step 2 of the kind's README).
  • Flash bytes: the table in flash and the code at -O2 for the board's core; RAM bytes: the table in RAM (step 4 of the kind's README). A table "RAM (copied at start by the image)" counts in both: its bytes stay in flash as the values the start-up code copies (step 11). libcrc and CRC++ build their tables in RAM themselves, at run time.
  • The board's CRC unit, the last row where the board has one, labelled "the board's CRC unit, driven by our code; not a library": the STM32 CRC unit or the RP2350's DMA sniffer, driven by our code (adapter_hw.c). Its class is "hardware unit" and it has no table. Its bytes are those of our adapter code, read from the board images. On the Pico 2 the unit is a DMA transfer that the CPU waits for; for CRC-32 on the STM32 unit the final XOR is in our code.
  • 16 B: cycles of one call on a message of 16 bytes at an 8-byte boundary, the mean of 256 calls.
  • per byte: (mean at 1024 bytes − mean at 256 bytes) / 768, at an 8-byte boundary.
  • Every number is the range over the eight placements (the configuration's code moved by 0, 4 ... 28 bytes), first pass; one number where all eight agree. A difference between two rows is a difference only where their ranges do not overlap (the method, "What the placements show").

The other lengths (1, 4 and 64 bytes), the message one byte after an 8-byte boundary, the second pass, the minimum, maximum and first call of every scenario, and the baseline (the bitwise reference, timed in the same image) are in the records. The 1-byte figures are not shown: at an 8-byte boundary with the cache on, that scenario is the first one after the cache is switched on (method, "A mean includes the first call").

What the tables show

Each sentence names the rows it rests on; the rows are those of the tables above.

  • The same class from two libraries. With the cache on, ETL crc32_t256 and crcany crc32iso_hdlc_byte, both a CRC-32 table of 256 in flash, have the same per-byte figure on five boards (nRF5340 DK 10.0, Raspberry Pi Pico 2 H 10.0, NUCLEO-G474RE 14.7, NUCLEO-H723ZG 8.0, NUCLEO-G0B1RE 15.0); on the SAM D20 Xplained Pro they are 15.3–15.6 and 14.3–14.6. Their 16-byte figures differ (NUCLEO-G474RE: 257–258 and 280–281), which is the part of a call that does not grow with the message.
  • The same instructions, the table in flash or in RAM. ETL crc32_t256 and libcrc crc_32 run the same loop instructions on the Cortex-M4, M7 and M33 cores (the report, check 3); libcrc builds its table in RAM. With the cache on, the NUCLEO-G474RE gives 14.7 and 10.0 cycles per byte for the two rows, the NUCLEO-H723ZG 8.0 and 8.0.
  • The placements, with the cache off. On the SAM D20 Xplained Pro every row of the cache-off tables is one number: the eight placements agree. On the NUCLEO-H723ZG, crcany crc32iso_hdlc_bit (CRC-32, bitwise) costs 41.0–225.0 cycles per byte with the cache off and 41.0–42.0 with it on: at its best placements the same with the cache off as on (the report, check 7).
