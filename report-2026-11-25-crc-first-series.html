The answer to the open question: per library or per algorithm?

Neither alone (the comparison is in the README):

  • On the Armv7-M and Armv8-M cores (M4, M7, M33), the C and C++ code of the same class often compiles to the same instructions per byte: CRC-32 with a table of 256 from ETL, crcany and libcrc; CRC-8 with a table of 256 from ETL, crcany and AceCRC; CRC-16 from crcany and libcrc.
  • It does not for the Rust crate (a down-counter, and an unrolled loop at -O2), for CRC++, for the tables of 16 of CRC-8, and for most pairs on the Cortex-M0+.
  • Where the instructions are the same, the data may not be: libcrc's table is in RAM, crcany's CRC-32 table is 4 KB against ETL's 1 KB. On a board whose cache holds only part of a table (below), that alone can change the cycles.

How sure: the instruction comparison is a fact of these builds (and of the loop chosen as the work loop; loops.py says how it chooses). That equal instructions give equal cycles is a hypothesis; the first series tests it.

What it means for the page: one line per configuration, grouped by CRC and class, with the libraries that compile to the same loop marked as such. If the first series shows equal cycles for equal loops, the page can fold them into one line per (algorithm, table location) and name the libraries; if not, the lines stay apart and the difference is itself the finding.

The table in flash, and copied to RAM

  • In flash is how ETL, crcany, AceCRC, Zephyr, zlib and the crc crate ship their tables (const); libcrc and CRC++ build theirs in RAM at run time, so they are measured with the table in RAM as shipped.
  • Copied to RAM for a flash-table configuration would be a second image of the same configuration: the table's section placed in .data by the linker script (a script of the kind's own, by the table's symbol name from sizes.tsv), so the library's code is unchanged and only the table's address moves. For the 15 configurations with a table in flash that is 120 more images in 7 more segments: 20 more flash writes on the six boards (nRF5340 2, G0B1 4, G474 4, H723 2, SAM D20 7, Pico 2 1; counted the same way as above, an estimate). Proposal: not in the first series; decide after it, per board, where "cache on" does not cover table reads (below).

Placement

  • Code: the method of version 2 applies (eight placements, the far call), with one difference in the image: the placement bytes lie before the adapter, not behind it, so the adapter and the library move together (kinds/crc/README.md, step 7). In version 2 the adapter stays; here that would leave the loop of a library of headers (ETL, CRC++), which is compiled into the adapter, at one address in all eight placements. Whether eight are needed at 1024 bytes: at that length the call is dominated by the loop, so placement may matter less than for a ring-buffer push; but the loop is short (5 to 18 instructions per iteration, up to 32 where the Rust crate unrolls it) and its alignment against the flash line and the cache line is exactly what placement varies. Not known before measuring.
  • The table: a new axis. With the table in flash it moves with the code in every placement, so the eight placements also move the table by 0 to 28 bytes; its alignment against a 32-byte cache line changes with it. A table in RAM does not move.
  • How a small first run settles both: one board (the NUCLEO-G474RE, where flash wait states and a small D-cache make placement and table alignment matter most), four configurations (ETL crc32_t256, ETL crc32_t16, crcany crc32iso_hdlc_word, zlib crc32), all eight placements, plus the same four with the table aligned to 32 bytes (aligned on a copy of the table is not possible without changing the library, so by the linker script of the kind: ALIGN(32) before the table's input section). That is 64 images in about 4 segments: 2 flash writes on that board. The spread over the eight placements and between the two table alignments tells whether eight placements and a table axis are needed for the full series.

The waits. The runner reads an image's results after a wait; if the image has not finished, it repeats the run with twice the wait (kinds/crc/bench/run-crc.py, lines 237-272). The longer wait is kept for that configuration for the rest of the board's runs (both passes, all placements), and after a run has finished the board's default becomes the shortest wait that has finished (state["wait"] = min(finished)). So the first run of a board sets the default, and a configuration that is slow at its first look keeps a longer wait: on the G474 crcany crc32iso_hdlc_bit (10 s in all 16 of its runs, one second attempt); on the G0B1 the first run (5 to 10 s, the board's default after) and crcany's bitwise code (20 s); on the nRF5340 nine configurations at 20 s; on the H723 eight configurations at 10 s and six at 20 s; on the SAM D20 and the Pico 2 the first run alone (5 to 20 s, and 5 to 40 s), after which every run used that wait. 27 runs needed more than one attempt; every one finished.

The numbers, checked (step 3)

Every number here is printed by a program from the 120 records: lab/tools/crc-series-checks.py (noise, perbyte, sameclass, offset, cache, ram, period), crc-loops.py and crc-placement.py (the built images of commit 6301058). The flash facts are quoted in lab/plans/2026-11-24-crc-flash-read-sources.md. "Per byte" is (mean at 1024 bytes − mean at 256 bytes) / 768 at offset 0; "rest" is what that line leaves at length 0; a range is min–max over the eight placements, first pass.

1. Noise floor. On five boards all 7680 means of a board are the same in both passes, to the cycle; the baseline (the reference of each CRC) measures the same in every image of a board, at every placement and in both passes (for example the G474's CRC-32 baseline at 1024 bytes: 156708 cycles cache off, 56338 cache on, in all 144 runs). On the Pico 2, 90 of 7680 means differ, all of the configuration, all cache on (the largest 1.26 %); in all 90 the minimum of the 256 calls is the same in both passes, the maximum differs in 44, and the slowest call of the scenario is its first call in at least one pass in 71 of the 90 (in both in 51). Which way of the two-way XIP cache is replaced on a miss is not stated in the RP2350 datasheet (RP-008373, 4.4.1 "XIP cache" says "two-way set-associative"; no replacement policy found). Closing line: at one position the repeat error is 0 on five boards and up to 1.26 % (cache on) on the Pico 2; what limits a comparison between two configurations is the spread over the placements (check 7), not the repetition.

The first call in the page's figures (first, every configuration and placement, first pass). A scenario's mean includes its first call. In the figures a page would show (16 bytes, and the cost per byte from 256 and 1024 bytes; offset 0), the first call's excess over the minimum is at most 2.45 % of the mean (Pico 2, 16 bytes, cache on, zlib at placement 0: first 1211, minimum 159, mean 168.0) and at most 0.25 % on the other five boards; leaving the first call out would change a cost per byte by at most 0.24 % (Pico 2, zlib at placement 16: 6.688 with, 6.704 without). The mean lies further above the minimum than the first call accounts for in some scenarios: up to 46 % on the Pico 2 (16 bytes, cache on, crcany's slicing by 4 at placement 28: mean 269.1, minimum 146) and 35 % on the G474 (16 bytes, cache on, AceCRC at placement 12: mean 244.2, minimum 159); there the calls themselves vary.

2. Cost per byte, by class. Cache on, the classes order as their loops do on every board: bitwise 41 (H723) to 87–90 (G0B1, SAM D20) cycles/byte; tables of 16 13–33; tables of 256 5–20; crcany's slicing by 4 2.75 (H723) to 13.5 (G0B1); zlib's braided words 4.93 (H723) to 17.7 (SAM D20). Two values were looked at because they do not fit their class: libcrc's table of 256 in RAM is slower per byte than the tables in flash on the two Cortex-M0+ boards (G0B1 16–20 against 15, SAM D20 16 against 14.3–15.6, cache on): its loop there is 13 instructions against 10 for ETL and crcany (crc-loops.py); and the H723's bitwise code cache off spans 41 to 225 cycles/byte over the placements, its lowest equal to its cache-on value (41–42): see check 7. The rest at length 0 is largest for zlib (118 to 422 cycles on the Cortex-M boards, cache off and on) and crcany's slicing by 4 (52 to 211). Whether the classes' ranges (all configurations and placements of a class) overlap is printed by classes. Closing line: with the cache on, the classes lie in separate bands of cost per byte in 14 of the 18 board and CRC tables; they overlap in four: zlib's braided words with the tables of 256 for CRC-32 on the G474, the G0B1 and the nRF5340 (on the G474 12.1 against 10.0–14.7), and Zephyr's shifts and XORs with the tables of 256 for CRC-16 on the G0B1. With the cache off they overlap in 9 of 18.

3. The same class from several libraries. The loops (crc-loops.py, placement 0): ETL and libcrc's CRC-32 table of 256 are the same instructions on the M4, M7 and M33 cores (7); crcany's differs only in the pointer increment; the Rust crate's loop is unrolled four times (25 instructions, 4 table loads); ETL and AceCRC's CRC-8 table of 256 are the same instructions on the M4, M7 and M33, and all three CRC-8 tables of 256 on the G0B1; ETL and Zephyr's CRC-32 table of 16 are the same instructions on the G0B1. The means (sameclass): with the cache on, the per-byte ranges of one class overlap only where the loops are the same or near it: CRC-8 table of 256 on G474, G0B1, H723 and SAM D20; CRC-32 table of 16 on G474, G0B1, nRF5340 and H723. With the cache off they overlap more often (on the H723 every class), because the placement ranges are wider. The mean at 16 bytes differs between libraries of one class even where the per-byte cost is the same (for example ETL against crcany, CRC-32 table of 256, G474 cache on: 257–258 against 280–281 cycles, both 14.70–14.72 per byte). Pairs with the same loop instructions but not the same cost per byte: ETL and libcrc's CRC-32 tables of 256 on the M4 and M33 cores. With the cache on the G474 gives 14.70–14.72 against 10.0, the nRF5340 10 against 9, the Pico 2 10 against 9; on the H723 (M7) the two are the same, 8 against 8. The report reads this as the place of the table (flash for ETL, RAM for libcrc; check 6), because the instructions are the same. Closing line: the same instructions with the table in the same kind of memory give the same cost per byte within the placement range; the same instructions with the table in flash against RAM do not (check 6); libraries of one class differ in the fixed part of a call, and per byte where their loops or their table's memory differ.
